# 网站 E2E 测试资料准备模板

这份文档用于接入任意新的测试网站。网址本身只解决“能否打开”，要生成稳定、可判断、可复用的 E2E 用例，还需要补齐下面的业务资料。

## 一、最小可执行资料

首次只想跑通一个效果，至少提供：

1. 测试环境地址和具体入口页面。
2. 网络访问方式：是否需要 VPN、hosts、代理、云桌面或特定浏览器。
3. 一个可登录账号及其角色；密码通过本机执行环境提供，不写进共享文档。
4. 一个明确的功能目标，例如“登录后查询订单列表”。
5. 一条完整操作流程：从什么页面开始，点击什么，输入什么，最后应该看到什么。
6. 流程所需的测试数据，例如订单号、客户名、文件、商品或已有记录。

有了这些内容，可以先生成并执行一条冒烟用例。

## 二、网站基本信息

```markdown
## 系统基本信息
- 系统名称：
- 环境名称：开发 / 测试 / 演示 / 预生产
- 应用根地址：
- 首个测试入口：
- 页面路由类型：普通路径 / hash 路由 / iframe / 多标签页
- 协议和端口：http/https，端口：
- 网络要求：VPN / hosts / 代理 / 云桌面 / 无特殊要求
- 执行端与服务端位置：本机 / 云桌面 / 容器；浏览器和被测服务是否在同一网络
- 域名与访问 IP：仅用于连通性诊断；页面执行仍使用域名
- 推荐浏览器：Chromium / Chrome / Edge / 其他
- 是否有证书、弹窗、下载或上传限制：
- 登录方式：账号密码 / SSO / LDAP / 短信 / 免登录 / 其他
- 登录成功后的落地页面：
- 登出方式：
- 顶部导航是否有“更多”或 `...` 溢出菜单：
- 关键功能的完整菜单路径（顶级菜单 → 父菜单 → 叶子页面）：
```

如果是内网虚拟主机，必须提供域名和访问 IP 的对应关系；执行时仍使用域名，不要只提供 IP。

## 三、功能清单

功能清单是生成测试范围和文件结构的依据。每行至少对应一个可独立验证的功能点。

| 编号 | 模块 | 功能点 | 角色 | 优先级 | 是否核心链路 | 前置数据 | 是否有副作用 |
|---|---|---|---|---|---|---|---|
| F-001 | 用户管理 | 查询用户列表 | 管理员 | P0 | 是 | 至少 1 个用户 | 否 |
| F-002 | 用户管理 | 新增用户 | 管理员 | P1 | 否 | 部门、角色 | 是 |
| F-003 | 订单管理 | 创建订单 | 销售 | P0 | 是 | 客户、商品 | 是 |

功能点命名要具体，避免只写“测试用户模块”“验证页面正常”。

## 四、业务流程说明

每个核心流程单独写一份，按真实用户操作顺序描述。

```markdown
## 流程：F-001 查询用户列表

### 前置条件
- 使用角色：管理员
- 已登录：否
- 必须存在的数据：至少一条用户记录
- 特殊开关/配置：无

### 主流程
1. 打开系统入口。
2. 登录。
3. 进入“用户管理 → 用户列表”。
4. 默认查看列表、总数和分页。
5. 输入用户名关键字并点击“查询”。
6. 查看过滤后的结果。

### 预期结果
- 登录成功后进入首页。
- “用户管理”和“用户列表”菜单可见。
- 列表、总数和分页展示正常。
- 查询结果只包含匹配记录。

### 异常和边界
- 关键字为空。
- 关键字不存在。
- 超长关键字。
- 特殊字符。
- 无权限角色访问该页面。

### 清理
- 本流程只读，不需要清理。
```

流程中必须区分“操作步骤”和“预期结果”。只给截图而没有文字流程时，无法可靠判断页面上的正确行为。

## 五、角色和权限矩阵

权限用例不能只提供一个管理员账号。

| 功能/页面 | 管理员 | 普通用户 | 只读用户 | 未授权用户 | 期望表现 |
|---|---|---|---|---|---|
| 用户列表 | 查看/新增/编辑 | 查看 | 查看 | 不可见 | 菜单和按钮按角色变化 |
| 用户删除 | 可用 | 不可用 | 不可用 | 不可见 | 禁用或拒绝并提示 |

需要说明：

- 每个角色的账号变量名。
- 权限是按用户、角色、组织还是数据范围控制。
- 权限变更后是否需要重新登录。
- 页面不可见、按钮禁用、路由拦截和提交拒绝分别是什么预期。

## 六、测试数据清单

| 数据类型 | 数据标识/规则 | 来源 | 是否可创建 | 是否需要清理 | 注意事项 |
|---|---|---|---|---|---|
| 用户 | 测试账号角色 | 环境预置 | 否 | 否 | 不在报告打印密码 |
| 订单 | `E2E-订单-UUID` | 用例创建 | 是 | 是 | 不能依赖固定第一条 |
| 上传文件 | `assets/sample.csv` | 项目文件 | 是 | 否 | 记录格式和编码 |

必须明确：

- 哪些数据已经存在，具体可用的查询标识是什么。
- 哪些数据由用例创建，唯一命名规则是什么。
- 数据之间的依赖关系。
- 是否允许修改或删除环境中的已有数据。
- 测试结束后的清理方式和负责人。

## 七、外部依赖

按实际情况提供，不需要的项写“无”：

```markdown
- 数据库：类型、用途、是否允许只读校验、连接变量名
- 文件服务：FTP/SFTP/对象存储、测试文件路径、读写权限
- 消息/任务服务：任务完成判定、最大等待时间、失败重试规则
- 邮件/短信：是否使用测试收件箱，是否允许真实发送
- 第三方登录/支付/地图：是否使用沙箱，回调如何模拟
- 浏览器下载目录：文件名规则、内容校验规则、清理规则
- 外部服务网络位置：与浏览器是否同网；FTP/SFTP/Hive/数据库是否需要云桌面或 VPN
```

外部服务不可用时，相关用例必须标记为环境阻断或跳过，不能伪造通过。

## 八、断言和验收标准

对每个功能点至少说明：

- 成功提示的准确文本或可识别页面元素。
- 列表、详情、状态、字段值和按钮状态的预期。
- 错误提示、校验规则和拦截行为。
- 异步任务的完成条件和最大等待时间。
- 文件下载/上传的名称、大小、格式和内容要求。
- 哪些错误属于业务缺陷，哪些属于环境问题。

固定等待结束、旧成功提示、页面没有报错或“视频里看起来点到了”都不能单独作为通过依据；异步和下载用例必须定义可见完成条件及必要的文件校验。

避免只写“操作成功”“页面正常”“接口返回正确”这类无法直接断言的描述。

## 九、已有资料和回归范围

请提供已有材料的路径或附件：

- 需求说明、原型、流程图或操作手册。
- Excel/禅道/缺陷单中的手工用例和历史失败用例。
- 现有回归清单、P0/P1 功能范围和版本信息。
- 已知缺陷、修复版本和需要回归的场景。
- 页面截图、字段说明、字典值和枚举选项。

已有资料只作为需求来源，最终自动化用例仍需落成明确的前置、操作、断言和清理步骤。

## 十、交付前确认表

- [ ] 地址、入口和网络方式已确认
- [ ] 登录方式、落地页和账号角色已确认
- [ ] 功能清单已按模块、优先级和副作用分类
- [ ] P0/P1 流程已提供主流程、异常和边界分支
- [ ] 权限矩阵已提供至少一个有权限和一个无权限视角
- [ ] 测试数据、创建规则和清理规则已确认
- [ ] 外部依赖和异步等待条件已确认
- [ ] 每个功能点有可见页面断言和验收标准
- [ ] 顶部溢出菜单、父子菜单路径和可见容器已探查
- [ ] 已知缺陷和回归范围已提供
- [ ] 密码等敏感信息只进入本地执行环境

## 十一、推荐接入顺序

1. 先用最小资料生成 1 条登录/访问冒烟用例。
2. 再提供功能清单，确定模块和优先级。
3. 为 P0 流程补充主流程、异常、边界和权限信息。
4. 校准真实页面选择器并执行只读用例。
5. 确认测试数据和清理策略后，再执行有副作用用例。
6. 最后按模块扩大范围并生成独立执行报告。
