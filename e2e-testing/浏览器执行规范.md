# 浏览器执行规范

## 1. 执行方式选择

### A. Playwright Chromium（默认）

用于可重复的自动化执行、冒烟、回归和报告生成。测试动作使用 `page.goto`、`getByRole`、`getByLabel`、`locator`、`fill`、`click`、`selectOption`、`setInputFiles` 等浏览器操作，结果使用页面可见元素断言。

示例：

```ts
await page.goto(entryUrl, { waitUntil: 'domcontentloaded' });
await page.getByRole('button', { name: '查询' }).click();
await expect(page.getByText('暂无数据')).toBeVisible();
```

### B. 浏览器 MCP（可选）

仅在当前 Agent 确实暴露这些工具时使用：

| 工具 | 用途 |
|---|---|
| `browser_navigate` | 打开 URL |
| `browser_snapshot` | 查看页面结构和可访问名称 |
| `browser_click` | 点击元素 |
| `browser_type` / `browser_fill_form` | 输入表单 |
| `browser_select_option` | 选择下拉项 |
| `browser_take_screenshot` | 保存证据 |
| `browser_console_messages` | 诊断控制台错误 |

MCP 不可用时不要停在工具名上，改用本地 Playwright Chromium 或让用户运行执行脚本。

## 2. 每个用例的操作循环

```text
准备前置条件
→ 打开真实入口
→ 登录并验证落地页
→ 读取页面结构
→ 执行一个用户动作
→ 断言页面可见结果
→ 记录关键证据
→ 清理本用例创建的数据
```

关键导航、提交、弹窗确认、异步任务完成和页面跳转后，必须重新观察页面状态，不能仅依赖等待时间或 URL 改变。

## 3. 定位与断言

- 优先级：可访问角色/名称 → label → 稳定文本 → `data-testid` → 明确的 CSS 结构。
- 避免依赖 `.nth()`、列表第一行、动态 class、内部接口响应和浏览器坐标。
- 断言用户能看到的结果：成功提示、错误提示、表格行、按钮状态、菜单可见性、字段值和页面标题。
- 网络请求、控制台和数据库信息只能用于诊断或经批准的后置校验，不能代替页面断言。
- 每个测试至少包含一个能证明业务结果的断言；“页面打开了”只属于可用性冒烟。

### 3.1 动态菜单和隐藏内容

- 先识别完整菜单树：顶级菜单、溢出菜单（`...`/`更多`）、父菜单和叶子菜单都要记录。
- 如果点击父菜单后只发生路由切换或模块切换，重新读取 DOM，再展开并点击叶子菜单；不要假定一次点击已经进入目标页面。
- 选择菜单项、分页、弹窗和下拉项时优先使用当前可见容器；同名隐藏模板节点不得被误选。
- 公共菜单工具应封装溢出展开、父菜单重试、可见节点筛选、SPA 稳定等待和调试日志；业务用例只描述菜单路径。
- 页面存在“显示更多”或折叠区域时，先展开再断言，不要把首屏未显示当成不存在。

### 3.2 异步结果与等待

- 等待时间只是上限，不是业务成功条件。使用状态文本、结果行、按钮状态、下载事件或文件校验确认完成。
- 查询、导出、上传、建表等异步操作要区分“已提交”“处理中”“成功”“失败”；不能用旧提示、页面未报错或固定 `waitForTimeout` 代替完成断言。
- 超时、下载失败和关键断言失败不能被空 `catch` 吞掉；如果业务允许继续执行后续用例，应让当前用例明确失败或待确认，并保留证据。

## 4. 严格禁止

- `fetch`、`axios`、XHR、直接调用后端 API 来完成业务步骤。
- `page.evaluate`/`browser_evaluate` 执行业务动作、多步逻辑或构造断言数据。
- 通过响应体、内部状态、数据库查询结果单独判定页面操作成功。
- 使用真实生产账号、固定共享数据或会泄漏密码的截图/日志。
- 用 `report('xxx', true)` 作为最终通过依据；最终状态必须由 Playwright 的真实测试结果生成。

补充：视频或截图只能证明当时页面显示了什么，不能单独证明异步任务已经完成；下载类用例还要核对下载事件、文件存在、文件名/格式和需求要求的内容或大小。

## 5. 失败留证

Playwright 项目应启用：

- `trace: 'retain-on-failure'`
- `screenshot: 'only-on-failure'`
- `video: 'retain-on-failure'`
- HTML 报告和每次执行的 Markdown 摘要

失败报告至少包含：用例文件和行号、失败步骤、错误摘要、截图/trace 路径、控制台异常、环境前置条件和建议分类。
