# 多线程 E2E 测试编排规范

本规范用于让一个主线程（编排者）协调多个子线程（执行者），分别处理多个 Playwright `.spec.ts` 文件。目标是缩短定位和修复时间，同时保证文件、测试数据、外部服务和最终报告不互相污染。

## 1. 术语和边界

| 名称 | 职责 | 不负责的事情 |
|---|---|---|
| 主线程 | 读取需求和报告、拆分任务、分配资源、处理公共代码、合并结果、最终回归和发布结论 | 不把未经复核的子线程结果直接当最终通过 |
| 子线程 | 处理主线程明确分配的 TS 文件或独立模块，校准页面、修复用例、执行定向测试、提交证据 | 不修改其他子线程文件、公共配置或全局规范；不扩大测试范围 |
| Playwright worker | 在一个 Playwright 进程内运行测试实例 | 不是 AI 子线程，不能替代任务拆分和资源隔离 |
| 资源锁 | 标识共享页面、账号、表、文件目录、FTP/SFTP 路径、任务队列等互斥资源 | 不允许用“尽量错开”代替明确的互斥规则 |

AI 子线程并发和 Playwright `workers` 是两层并发：前者决定有多少个修复任务同时进行，后者决定一个测试命令同时运行多少个用例。修改型用例默认每个子线程使用 `--workers=1`；不能通过增加 Playwright worker 解决测试数据冲突。

## 2. 主线程的唯一控制权

主线程必须维护本轮任务清单，并拥有以下最终决定权：

1. 哪些 TS 文件可以并行，哪些必须按依赖顺序执行。
2. 每个子线程可以修改的文件、测试数据前缀、外部服务路径和最大副作用。
3. 公共工具、Playwright 配置、环境变量模板、skill 和报告模板的修改。
4. 失败分类：定位、环境、数据前提、业务缺陷、用例设计或结果有效性。
5. 是否接受子线程结果、是否需要回滚局部改动、是否进行最终串行回归。

子线程不能自行把“暂时跳过”“超时结束”“没有看到错误”改写为通过，也不能自行降低断言、延长超时或删除失败证据来消除红灯。

## 3. 任务拆分规则

### 3.1 拆分单位

- 优先按完整 TS 文件或功能模块拆分；同一 TS 文件默认只分配给一个子线程。
- 如果必须拆分同一 TS，必须按测试名称明确分段，并由主线程负责合并；两个子线程不能同时编辑同一文件。
- 公共工具、配置和报告文件单独设为“主线程任务”，不要让多个子线程同时修改。
- 子线程只接收有明确 Excel 行号、测试名称、目标页面和验收条件的任务。

### 3.2 可并行和必须串行的场景

| 场景 | 处理方式 |
|---|---|
| 只读查询、菜单访问、页面展示 | 可并行；每个子线程使用独立浏览器上下文 |
| 各自创建 UUID 表/任务/文件且路径隔离 | 可并行；必须声明前缀和清理责任 |
| 修改或删除同一任务、同一表、同一账号权限 | 串行并加资源锁 |
| 上下线、执行、停止、审批等状态机操作 | 同一业务对象串行；不同对象可并行 |
| FTP/SFTP 同一目录、同一远程文件名 | 串行或为每个子线程分配独立目录 |
| 数据库建表 | 可并行，但表名必须带 `E2E_<runId>_<taskId>`；禁止触碰原有表和数据 |
| 权限变更、登录态、全局配置 | 串行；完成后重新登录并复核 |
| 需要先创建数据源/父目录/测试表的用例 | 先由准备任务完成，再放行依赖子线程 |
| 公共导航工具或选择器策略变更 | 主线程处理，完成后子线程重新拉取最新版本 |

### 3.3 资源隔离最低要求

每个子线程启动前必须得到以下信息：

```markdown
任务编号：
负责 TS：
Excel 行号/测试名称：
目标页面和完整菜单路径：
只允许修改的文件：
允许读取的测试数据：
本线程创建数据前缀：
数据库允许操作：仅新建/查询本线程对象；禁止修改原有表和数据
FTP/SFTP 允许目录：
资源锁名称：
最大单用例耗时：
通过条件：
阻断条件：
```

没有资源锁、数据前缀或清理责任时，子线程只能做只读探查，不能执行有副作用操作。

### 3.4 并发槽位和强资源故障处理

多线程任务同时受到 AI 子线程槽位、浏览器进程、页面服务承载能力和报告文件锁的限制。之前出现过“上一轮子线程已经完成但仍占用并发槽位，继续分发时报 `agent/thread limit reached`；多个 Playwright 进程共用默认 HTML 报告目录导致互相等待”的问题，统一按以下规则处理：

1. 主线程维护活动线程表，状态为完成、失败、阻断或不再需要的线程都立即关闭并从活动表移除；不能只等待其返回消息而继续占用槽位。
2. 新任务按未完成队列补发，禁止重复启动已经完成的任务；发生并发上限错误时先回收旧线程，再只补发缺失任务。
3. 每个 AI 子线程使用独立的 `E2E_RUN_ID`、`HTML_REPORT_DIR`、`TEST_RESULTS_DIR`；报告、截图、视频、trace 和 Markdown 文件不得共享写入路径。
4. 每个修改型 Playwright 进程默认 `--workers=1`。机器变慢时先把 AI 子线程降到 2～3 个，不能用增加 Playwright worker 的方式硬顶资源。
5. 同一页面服务或共享账号出现连续超时/登录失败时，暂停依赖该资源的队列，先做一次公共环境检查；不要让多个线程重复重试同一个阻断。
6. 一轮子线程完成后，主线程先检查越界修改和证据，再关闭线程、补发下一批；只有活动线程数和报告目录都确认隔离后才能继续并发。

推荐的 Windows 执行变量示例：

```cmd
set "E2E_RUN_ID=W01-%RANDOM%"
set "HTML_REPORT_DIR=temp\reports\%E2E_RUN_ID%"
set "TEST_RESULTS_DIR=temp\results\%E2E_RUN_ID%"
call node_modules\.bin\playwright.cmd test <自己的TS文件> --project=chromium --workers=1
```

主线程最终回报中必须说明：本轮最大 AI 子线程数、实际同时运行数、是否发生资源降级、每个线程的报告目录，以及是否已回收完成线程。

## 4. 子线程允许和禁止的动作

### 允许

- 阅读项目规范、配置、需求 Excel、失败报告、截图、视频和 trace。
- 在分配的 TS 文件中校准真实页面定位、等待和页面断言。
- 使用 Playwright Chromium 做页面操作；执行与自己任务相关的定向测试。
- 在自己隔离的数据前缀、表、FTP/SFTP 目录中创建和清理数据。
- 生成自己的诊断日志、截图、视频和 trace，并写入本线程专属 run/task 目录。
- 发现公共问题时向主线程提交修改建议和最小复现，不直接抢改公共文件。

### 禁止

- 修改其他子线程负责的 TS、公共 `utils.ts`、Playwright 配置、包依赖、skill 或报告模板。
- 使用 `test.only`、跳过关键断言、吞掉异常、把固定等待当完成条件。
- 通过 API、数据库结果或 `page.evaluate` 完成浏览器业务动作。
- 修改、删除或覆盖既有业务表、业务数据、共享 FTP 文件、共享目录或其他线程创建的对象。
- 复用“列表第一行”“固定任务名”“固定远程文件名”作为有副作用操作对象。
- 打印账号密码、完整连接串、令牌或包含敏感信息的截图标题。
- 为了让测试变绿而扩大超时、放宽文本匹配到没有业务意义，或将环境阻断标记为通过。

## 5. 主线程执行流程

### 阶段 A：盘点和拆分

主线程先执行静态检查和 `playwright test --list`，读取最近报告，建立任务表：

| 任务 | TS 文件 | Excel 行 | 类型 | 资源锁 | 前置任务 | 子线程 | 状态 |
|---|---|---:|---|---|---|---|---|
| T01 | `模块/01-查询.spec.ts` | 1-5 | 只读 | `menu:模块A` | 无 | W01 | 待执行 |
| T02 | `模块/06-新增.spec.ts` | 6-8 | 写入 | `db:W02` | T00 | W02 | 待执行 |

拆分时先处理共同阻断项：网络、登录、顶部菜单展开、数据源、父目录、数据库或 FTP。不要让五个子线程重复验证同一个环境阻断。

### 阶段 B：分配和启动

- 默认启动 2～5 个子线程；根据机器性能、页面服务承载能力和资源锁动态减少。
- 只读任务可以先并行；写入任务必须确认数据前缀和资源锁后再启动。
- 每个子线程使用独立 `E2E_RUN_ID` 和证据目录；不要共用正在写入的 HTML 报告目录。
- 子线程命令应限定到自己的 TS 文件或 grep 范围，不允许默认启动全量套件。

示例：

```text
主线程：分配 W01 → e2e/数据服务/38_39_40.spec.ts
子线程 W01：npx playwright test e2e/数据服务/38_39_40.spec.ts --project=chromium --workers=1
主线程：分配 W02 → e2e/数据地图/05_06.spec.ts
子线程 W02：npx playwright test e2e/数据地图/05_06.spec.ts --project=chromium --workers=1
```

### 阶段 C：监控和收敛

主线程只关注状态、阻断和资源冲突，不重复接管子线程的页面操作。子线程出现以下情况必须暂停并回报：

- 发现可能影响原有数据、共享文件或其他线程对象的操作。
- 账号权限、网络或公共菜单问题导致多个用例无法继续。
- 需要修改公共工具、配置或另一个线程的文件。
- 需求描述与实际页面不一致，无法在不猜测的情况下定义断言。
- 同一失败连续重现，且继续重跑不能提供新证据。

一个子线程失败不应自动停止无依赖的其他子线程；但公共环境阻断、数据安全风险或公共代码冲突时，主线程应暂停相关任务并重新排队。

### 阶段 D：合并和最终验收

1. 主线程检查每个子线程的文件改动，确认没有越界文件。
2. 先合并公共工具，再合并各 TS；发生冲突时由主线程决定，不让子线程互相覆盖。
3. 执行 TypeScript 检查、测试列表检查和目标 TS 定向回归。
4. 对通过用例复核视频/trace 是否真正达到业务完成条件，排除超时假通过。
5. 对修改型链路按资源锁串行回归，最后生成统一 HTML 报告和 Markdown 汇总。

## 6. 子线程回报格式

子线程完成或阻断时必须返回以下信息：

```markdown
任务编号/线程：T01 / W01
负责文件：绝对路径或项目相对路径
修改摘要：
执行命令：
TypeScript 检查：通过 / 失败
定向测试：通过 N / 失败 N / 跳过 N / 阻断 N
失败分类：定位 / 环境 / 数据 / 业务 / 用例设计 / 结果有效性
证据：截图、视频、trace、日志的路径
数据清理：已完成 / 未完成及原因 / 无需清理
未解决问题：
需要主线程处理：是 / 否
```

“通过”必须来自 Playwright 的真实测试结果；`report()`、截图存在或子线程口头确认不能替代测试状态。

## 7. 结束条件

本轮多线程任务只有同时满足以下条件才算完成：

- 所有分配的 TS 都有明确的通过、失败、跳过或环境阻断状态。
- 没有未处理的文件冲突、资源锁冲突和越界修改。
- 失败用例已经按类别归档，不能把定位问题、环境缺失和业务缺陷混成一类。
- 通过用例没有依赖自动超时、旧提示、空 `catch` 或未验证的异步任务。
- 主线程完成最终类型检查、定向回归和统一报告；子线程报告仅作为输入。
