# E2E 测试用例编写规范

## 1. 用例必须可执行、可判断、可复现

每条用例至少明确：

- 用例 ID、模块、优先级和来源（需求/Excel/缺陷回归）。
- 前置条件：账号角色、菜单权限、数据记录、配置项和外部服务。
- 操作步骤：按用户实际操作顺序描述，动作粒度清晰。
- 预期结果：每个关键动作对应页面可见断言。
- 清理策略：删除或标记本用例创建的表、任务、API、文件或权限。

推荐结构：

```ts
test('TC-DM-001 查询列表：条件查询与分页', async ({ loginPage }) => {
  const page = loginPage;
  await clickMenu(page, '数据地图', '表查询');

  await fillByLabel(page, '表名', `不存在_${uuid()}`);
  await page.getByRole('button', { name: '查询' }).click();

  await expect(page.getByText(/暂无数据|没有数据/).first()).toBeVisible();
});
```

## 2. 场景覆盖

每个功能模块按实际适用性覆盖：

| 类型 | 必须验证 |
|---|---|
| 正常流程 | 有效输入完成主流程并验证业务结果 |
| 异常路径 | 必填缺失、错误格式、无权限、重复数据、服务不可用时的提示和拦截 |
| 边界值 | 空值、最大/最小值、超长值、特殊字符、分页边界和大文件 |
| 权限 | 有权限可见/可操作，无权限不可见/被拦截 |

异常和边界用例必须断言“被拦截或提示正确”，不能只断言页面没有崩溃。

## 3. 数据隔离与副作用

- 新建数据名称使用 UUID 或等价唯一后缀，并在报告记录该标识。
- 不依赖“列表第一行”、其他测试刚创建的数据或固定执行顺序。
- 有顺序依赖时使用 `test.describe.serial`，并在注释中说明原因。
- 创建/编辑/删除/上线/审批/停止/kill 之类的用例必须标记副作用和清理责任。
- 清理失败要单独记录，不能覆盖原测试结果。
- 只读冒烟与有副作用回归分组，默认先跑只读组。

## 4. 选择器与断言

- 优先使用角色、可访问名称、label、稳定文本或 `data-testid`。
- 选择器不应依赖动态 class、坐标、脆弱的 DOM 层级或无说明的 `.nth()`。
- 页面断言优先于 URL 断言；URL 只能作为路由辅助确认。
- 每条用例必须至少有一个直接证明业务结果的断言。
- 控制台 error 作为辅助质量门禁；需要忽略时使用受控的 `CONSOLE_ALLOWLIST`，并在环境清单记录原因。

## 5. 报告与“假绿”防护

- 不在用例中硬编码“通过”作为最终结果。
- 自定义 `report()` 只能记录步骤详情；最终通过/失败由 Playwright 的 `testInfo.status` 生成。
- 断言之后仍有步骤时，不得提前写最终通过结论。
- 报告区分 passed、failed、skipped、fixme、blocked 和未执行。
- 报告必须关联命令、浏览器、环境入口、用例文件、行号和证据路径。

## 6. 权限闭环

涉及角色和权限的用例按闭环编写：

1. 准备角色/权限并验证目标用户可见、可操作。
2. 撤销或变更权限后重新登录/刷新会话。
3. 验证菜单、按钮、路由和后端拒绝表现均符合预期。

如果环境只有一个管理员账号，不能声称完成了无权限验证，应标记为环境缺口或跳过。
