# E2E 测试 Skill

## 总原则

1. 默认使用本地 Playwright Chromium 执行可重复的自动化测试；不要把 MCP 当成必需依赖。
2. MCP 仅用于交互式页面探索、观察 DOM/无障碍树和校准选择器；当前会话未暴露 MCP 工具时，改用 Playwright Chromium 或让用户在本地执行。
3. 业务操作必须通过浏览器可见操作完成：导航、点击、输入、选择、上传和页面断言。禁止用 `fetch`、`axios`、XHR、接口响应或 `page.evaluate` 代替用户操作或页面断言。
4. 数据库/FTP 只能作为已获准的辅助后置校验，必须在环境清单中显式配置。执行完整报告时不要用 `test.skip`/`test.fixme` 隐藏环境缺失：让用例执行到可判断的前置检查并抛出明确的环境阻断错误，由独立的环境阻断报告汇总；只有用户明确要求“只跑可用样本”时才允许单独的跳过模式。
5. 测试账号、密码、令牌和连接密码不写入 skill、报告、截图标题或提交到仓库；使用本地环境变量或未纳入版本控制的执行脚本。
6. 先跑只读冒烟，再跑有副作用的用例；全量执行前必须确认范围、数据影响和清理方式。

## 执行阶段

### 阶段 0：识别目标与范围

先读取项目根目录的 `环境检查清单.md`、Playwright 配置、用例目录和最近一次报告。若清单不存在，创建它并只记录非敏感信息。

确认以下内容：

- 被测系统域名、应用根地址和具体入口；hash 路由要记录完整入口。
- 执行机器：本机、云桌面、容器或远程 Agent；确认该机器能访问目标网络。
- 测试账号角色；只记录变量名和角色，不记录密码。
- 用例路径、浏览器、Node/包管理器和浏览器安装状态。
- 依赖的测试数据、数据库、FTP/SFTP、权限角色和清理责任人。

用户只要求“看效果”时，默认选择 1 条只读用例或专用 smoke 用例，不启动全量套件。

### 阶段 1：就绪检查

按以下顺序检查，任何一项失败都先反馈，不要把失败环境继续包装成用例失败：

1. 静态检查：`test.list`、TypeScript 类型检查、禁止 `test.only`。
2. 运行时检查：Node、包管理器、Playwright Chromium 可启动。
3. 网络检查：域名解析、TCP 端口、HTTP 页面状态；使用域名访问，不能只用 IP 替代虚拟主机域名。
4. 登录检查：账号变量存在，登录入口和落地页路径与真实页面一致；不在日志打印密码。
5. 数据检查：只读用例的数据前提存在；创建/删除类用例具备 UUID 隔离和清理策略。
6. 选择器检查：所有 `TODO[env]` 都要归类为已确认、待校准或阻断项。

### 阶段 1.5：动态菜单与页面结构校准

对使用 SPA、响应式布局、Element/Ant 风格菜单或顶部导航的网站，先做一次页面结构探查，再批量生成用例：

1. 记录从顶级菜单到叶子页面的完整路径；不要把“点击父菜单后路由变化”误认为已经进入最终功能页。
2. 探查顶部菜单是否存在 `...`、`···`、`更多` 等溢出入口。可见菜单不完整时，先展开溢出菜单，再定位隐藏模块。
3. 父菜单和叶子菜单可能需要分两次点击：第一次切换模块或路由，第二次展开子菜单。公共导航工具应支持重新观察 DOM、重复尝试和展开状态复核。
4. 同名节点可能同时存在于隐藏模板和可见菜单中；定位必须筛选 `:visible` 或使用可见的无障碍节点，不能默认取第一个匹配元素。
5. 页面跳转后同时等待 DOM 稳定和关键页面信号（标题、面包屑、表格、表单或菜单项）；不能只等待固定时间，也不能只依据 URL 变化。
6. 分页、弹窗、抽屉和下拉选项可能有隐藏副本；断言和操作必须锁定当前可见容器。
7. 项目已有 `页面页签工具.ts` 时，优先使用 `TabNavigator/clickTab` 处理页面内页签；不要在每个 TS 中重新实现不一致的“更多”展开逻辑。若旧用例已有局部 helper，先确认其覆盖范围，再逐步迁移到公共工具。
8. 对探查结果保留一张结构截图或诊断日志，并将稳定规则沉淀到公共工具类；不要把某次运行的动态 class、索引或坐标直接复制进用例。

### 阶段 1.6：复杂控件校准

以下规则来自真实页面中最容易造成假失败的控件组合，应优先沉淀到公共工具，不要在每个 TS 中重复猜测：

1. 隐藏页签：同时检查首屏可见页签、`...`/`更多` 溢出菜单、左右滚动控件和折叠区域；先展开，再在当前可见容器内按文本或角色定位。首屏未出现不等于功能不存在。
2. 级联下拉：类型→数据源→数据库→Schema 必须逐级等待并验证已选文本；字段标签大小写和中英文混排要兼容（例如 `schema`/`Schema`）。表单有 `*` 的字段全部填完，不能为了绕过下拉问题省略必填项。
3. 空值下拉框：带向下箭头、`role="combobox"` 或 Select 样式的空控件，不能按“没有输入框”跳过。先点击展开，读取当前可见选项，选择一个合法值，再提交并验证选中文本；例如“是否敏感”这类字段，选择“敏感”或“不敏感”都属于有效测试数据，关键是不能留空。若没有可见选项，才记录为环境/页面阻断。
4. 长下拉列表：只遍历可见选项；选项被滚动层拦截时先 `scrollIntoViewIfNeeded()`，再在已确认当前弹层的前提下点击。不要把固定 `nth()` 当作选项定位。
5. 分裂按钮：点击“新建”后若出现数据库选择菜单，应选择目标项并等待表单的关键保存/建表按钮出现；不能把按钮文字相同的菜单项、筛选项或隐藏副本当成表单已打开。
6. 表格固定列：操作列和名称列可能在左右固定表格中各渲染一次；优先从当前可见行和固定列容器定位，点击后复核 URL、弹窗或页面标题变化。
7. 弹窗/抽屉：操作前先判断目标弹窗是否已经可见。弹窗已打开时不要再次点击背景按钮；复选框、确定按钮和表格行都应限定在当前弹窗容器内。
8. 编辑器：Monaco 优先用可访问名称 `Editor content;Press Alt+F1` 定位；不能用 `textarea.first()` 猜测，因为它可能命中描述字段。执行 SQL 后检查当前结果页签的错误文本，不能把上一条 SQL 的 `true` 当成本条成功。

### 阶段 1.7：TS 开发的本地模型三步流水线

涉及后端业务理解、TS 开发与页面回归的任务，按以下顺序分工，前一步产物应成为后一步的输入：

1. `glm-5.3` 读取后端代码，梳理业务模型、角色/权限规则、接口与数据库关联，明确测试前置、测试数据和页面断言。输出应区分已由代码证实的规则、待页面确认的规则和未知项。
2. `glm-5.3` 基于已明确的规则开发或修改 TS：抽取公共工具、补充断言、处理测试数据隔离，并执行静态检查。不要在业务逻辑尚未明确时依靠猜测批量生成页面操作。
3. `glm-5.3-flash` 执行页面用例，结合失败截图、视频、trace 和真实 DOM 结果校准定位、等待和控件交互；修复后以串行 Playwright 回归结果验收。

模型任务完成不等于用例通过。主线程必须核对实际改动、测试命令、报告和失败证据；模型服务限流、超时或不可用时，记录任务未完成，不得把未验证改动写成已修复。

### 阶段 2：执行测试

优先使用 Playwright Chromium：

```text
corepack pnpm exec playwright test --list
corepack pnpm exec playwright test <spec-or-grep> --project=chromium --headed
```

执行规则：

- 默认串行执行 `workers=1`，避免共享环境中的任务、表和权限状态互相污染。
- 只读用例可先执行；创建、编辑、删除、上线、审批、停止或 kill 会改变环境的用例，要在执行前明确标记副作用。
- 不使用 `test.only`、硬编码第一行数据、固定顺序依赖或“点击后直接写通过”的报告调用。
- 用例失败时保留 trace、截图、视频和控制台错误；先按登录/网络、选择器、数据前提、业务缺陷分类。
- 完整报告模式禁止实际跳过：静态检查必须确认没有 `test.skip`、`test.fixme`、`describe.skip`、`test.only` 等标记；环境缺失用明确异常结束当前用例，并写入独立环境阻断报告。报告必须同时给出实际 skipped 数量，避免把“环境阻断”误报成 skipped 或 passed。
- 不要用无条件 `catch` 吞掉下载、任务轮询、弹窗确认或关键断言超时；确需容错时必须记录原因，并在最终断言中明确“不确定”不能算通过。
- 异步任务必须以页面可见的完成状态、结果行、下载完成事件并结合文件属性/内容等验收条件判定完成；固定等待结束、旧成功提示或“页面没有报错”都不能单独作为通过依据。
- 清理动作不能覆盖主断言：记录 `primaryError` 和 `cleanupError`，优先报告主失败，同时保留清理失败证据；只有确认资源已经创建后才执行删除。
- 成功提示不要写死单一文案；优先在当前可见消息容器内匹配同义成功文案，并同时验证业务状态、结果行或页面跳转，避免把按钮文字、旧 toast 或旧结果页签误当成功。

如果使用 MCP 探索页面，遵循 `浏览器执行规范.md`；探索结果应沉淀为稳定的 Playwright 定位和断言，不能把一次性人工操作当成自动化完成。

### 阶段 2.1：多线程编排

当需要同时处理多个 TS 文件时，使用一个主线程统一编排多个子线程，遵循 `多线程E2E测试编排规范.md`：

- 主线程负责拆分任务、分配 TS 文件和资源锁、处理公共配置/工具、合并改动、最终回归和统一结论。
- 子线程只处理被分配的 TS 文件或模块，并返回命令、改动、测试状态、证据、清理结果和阻断原因。
- 同一 TS、公共工具、Playwright 配置、skill、报告模板和共享测试数据不得由多个子线程同时修改；只读共享数据确认无状态污染后才能并行使用。
- 只读用例可以并行；修改同一任务、表、权限、FTP/SFTP 目录或状态机对象的用例必须串行或使用独立资源锁。
- AI 子线程并发与 Playwright `workers` 分开控制；修改型用例默认每个子线程使用 `--workers=1`，不能靠增加 worker 解决数据冲突。
- 启动新子线程前先检查并发槽位；已完成、失败或不再需要的子线程必须立即回收/关闭。遇到“agent/thread limit reached”时，禁止重复提交相同任务，先回收旧线程，再按未完成队列继续分发。
- 并行执行必须为每个线程设置独立的 `E2E_RUN_ID`、`HTML_REPORT_DIR` 和 `TEST_RESULTS_DIR`；禁止多个 Playwright 进程共用默认 HTML 报告目录、截图/视频目录或 Markdown 报告文件。机器资源紧张时优先减少 AI 子线程数量，再保持每个修改型 Playwright 命令 `--workers=1`。
- 子线程不能将超时、旧提示、吞掉的异常或截图存在当作通过；最终状态必须由主线程复核真实 Playwright 结果。

### 阶段 3：报告与复盘

每次执行创建独立 run 标识或清理同一 run 的旧报告，报告必须区分：通过、失败、跳过、fixme、未执行和环境阻断。报告中记录命令、浏览器、目标入口、耗时、失败分类和证据路径，不写入密码或完整敏感连接串。

报告模板见 `测试报告规范.md`。报告只反映本次执行，不把上一次失败的残留内容混入本次汇总。

通过结果也要复核有效性：检查是否在最大等待时间内真正达到业务完成条件，是否因自动结束、空列表、旧提示、未展开页面或被吞掉的异常而产生假通过。下载类用例至少核对下载事件、文件存在、文件名/格式，以及在需求要求时的大小或内容。

## 失败处理优先级

1. 浏览器未启动、DNS/TCP/HTTP 不通：修复执行环境。
2. 登录失败或落地页不一致：校准入口、账号变量和登录选择器。
3. 菜单、表单、表格定位失败：按真实 DOM 校准选择器。
4. 数据前提缺失：补充测试数据；完整报告模式记录为环境阻断，样本模式才按明确原因跳过。
5. 页面行为与预期不符：保留证据，作为业务缺陷报告。

补充判断：如果页面明确提示“对象未接入/未登记/无权限/不允许操作”，先确认这是产品业务规则还是测试数据缺失；不能为了让 SQL、表格或权限用例变绿而放宽断言，也不能把未登记对象的查询结果当成成功。

复盘时还要单独区分：

- 页面结构/定位问题：菜单未展开、隐藏副本被选中、父子菜单路径不完整、可见性或分页容器判断错误。
- 环境前置问题：VPN、云桌面网络、FTP/SFTP、Hive、数据库、角色账号或测试数据未准备。
- 用例设计问题：需求描述与实际页面不一致、业务闭环不完整、权限预期不明确、清理策略缺失。
- 结果有效性问题：超时自动结束、异步任务尚未完成、下载未核验、异常被吞掉；这类结果应回收为“待确认”或失败，不保留为通过。
