# 字段血缘初始化与断言清单

用途：为湖南中行环境的字段级血缘测试准备一套固定、可重复使用的文件接入来源表、SFTP 来源表、GBase 目标表和任务调度 SQL。文件/SFTP 接入均直接自动建表到 GBase；数据地图目标表及任务调度同样使用 GBase，不操作已有业务表。

## 当前已实现用例：BL-FLD-01-01（文件与 SFTP JOIN）

文件接入表 `e2e_hn_gbase_fld_file_src` 与 SFTP 表 `e2e_hn_gbase_fld_sftp_src` 均由接入向导自动建到 GBase。数据地图新建 GBase 目标表：

`e2e_hn_gbase_fld_file_sftp_join_target_v2`

任务调度使用一条不带结尾分号的 `INSERT ... SELECT ... INNER JOIN`，同时读取文件接入表和 SFTP 表。它要验证的基础字段边包括：

- `file_id -> file_id`
- `sftp_id -> sftp_id`
- `file_amount -> file_amount`
- `sftp_amount -> sftp_amount`
- `shared_key`、`business_date` 分别进入同名目标字段

每个目标字段均从图谱展开后打开字段详情弹窗，并按“来源表前缀、来源字段、目标字段标题、SQL 自动解析边”逐条核验。字段弹窗默认仅展示该字段向上、向下各一级关系；验证跨中间表的长链路时，点击字段节点右下角加号继续展开上游或下游。基础边验证不需要展开长链路。

此前失败使用的是 MySQL 来源表，GBase 任务调度无法读取。现已改为同库 GBase 来源表；需先执行 `BL-FLD-00-01`、`BL-FLD-00-02` 建立新来源表，再重新验证本用例。任务调度保存后，图谱可能先只显示当前表、随后补齐来源节点；自动化会重新打开详情页读取三次。字段关系仍必须以字段详情弹窗为准。

## 2. 本地上传文件

文件接入使用：[e2e_lineage_file_source.csv](文件接入/e2e_lineage_file_source.csv)。以页面下载的 CSV 样本为基准，文件名和字段均调整为字段血缘专用夹具；本地文件接入页面仅支持 CSV，需保留 `.csv` 后缀；SFTP 远端文件仍保持无后缀。

文件接入与 SFTP 接入均使用逗号分隔、首行表头、UTF-8 编码；选择“自动建表”。字段映射的目标字段名必须保持为英文且唯一，不能出现中文、空格、重复列名或特殊字符。

## 4. 目标表 DDL

在数据地图新建表的 DDL 解析输入框中使用：

```sql
CREATE TABLE e2e_hn_gbase_fld_file_sftp_target_v1 (
  target_id BIGINT NOT NULL,
  shared_key VARCHAR(32) NOT NULL,
  source_file_name VARCHAR(128),
  source_region VARCHAR(32),
  file_amount DECIMAL(18,2),
  sftp_amount DECIMAL(18,2),
  total_amount DECIMAL(18,2),
  source_tag VARCHAR(32),
  business_date DATE
);
```

## 5. 目标表“任务调度”生产脚本

脚本类型选择 `G_BASE_DB`（页面可显示为 GBase）。本 SQL 是字段血缘的主验证脚本，不需要在自助查询中执行：

```sql
INSERT INTO e2e_hn_gbase_fld_file_sftp_target_v1 (
  target_id,
  shared_key,
  source_file_name,
  source_region,
  file_amount,
  sftp_amount,
  total_amount,
  source_tag,
  business_date
)
SELECT
  f.file_id AS target_id,
  f.shared_key,
  f.file_name AS source_file_name,
  s.region_code AS source_region,
  f.file_amount,
  s.sftp_amount,
  f.file_amount + s.sftp_amount AS total_amount,
  'FILE_SFTP' AS source_tag,
  f.business_date
FROM e2e_hn_gbase_fld_file_src f
INNER JOIN e2e_hn_gbase_fld_sftp_src s
  ON f.shared_key = s.shared_key;
```

先保存并上线上述主脚本，等待血缘异步解析完成。需要验证“旧血缘清除”时，临时改为以下无来源 SQL，保存并上线后确认关联消失；再恢复主脚本，确认关联重新出现：

```sql
SELECT 1 AS e2e_no_lineage;
```

## 6. 字段级预期关系

| 目标字段 | 预期来源字段 | 验证重点 |
|---|---|---|
| `target_id` | `e2e_hn_gbase_fld_file_src.file_id` | 同名外的别名映射 |
| `shared_key` | `e2e_hn_gbase_fld_file_src.shared_key` | 直接字段传递 |
| `source_file_name` | `e2e_hn_gbase_fld_file_src.file_name` | 别名映射 |
| `source_region` | `e2e_hn_gbase_fld_sftp_src.region_code` | 跨来源表字段 |
| `file_amount` | `e2e_hn_gbase_fld_file_src.file_amount` | 直接字段传递 |
| `sftp_amount` | `e2e_hn_gbase_fld_sftp_src.sftp_amount` | 跨来源表字段 |
| `total_amount` | `e2e_hn_gbase_fld_file_src.file_amount`、`e2e_hn_gbase_fld_sftp_src.sftp_amount` | 计算字段应有两个上游字段 |
| `source_tag` | 无 | 常量字段不得误产生上游字段血缘 |
| `business_date` | `e2e_hn_gbase_fld_file_src.business_date` | 指定单一来源字段 |

表级图谱应包含 `e2e_hn_gbase_fld_file_src`、`e2e_hn_gbase_fld_sftp_src`、`e2e_hn_gbase_fld_file_sftp_target_v1` 三个节点，以及两条来源表到目标表的边。边详情应能识别正确的来源表和目标表。

### 字段链路的最终验证方式

前端更新后，字段级断言按真实交互执行，不再只判断页面是否显示某个字段名：

1. 打开目标表 `e2e_hn_gbase_fld_file_sftp_target_v1` 的“数据血缘”。
2. 点击并展开目标表节点，显示该表字段。
3. 点击一个目标字段，打开字段血缘详情弹窗。
4. 在弹窗内核对完整链路的来源表、来源字段、中间计算关系和目标字段。

字段详情弹窗的链路才是字段级用例的最终判定对象。例如：

- 点击 `total_amount`：链路必须同时包含 `e2e_hn_gbase_fld_file_src.file_amount`、`e2e_hn_gbase_fld_sftp_src.sftp_amount` 和 `e2e_hn_gbase_fld_file_sftp_target_v1.total_amount`。
- 点击 `source_file_name`：链路必须包含 `e2e_hn_gbase_fld_file_src.file_name` 和 `e2e_hn_gbase_fld_file_sftp_target_v1.source_file_name`，不得错误关联 SFTP 字段。
- 点击 `source_tag`：应明确没有上游字段链路，不能误展示文件或 SFTP 来源字段。

自动化断言顺序固定为“表级节点与边 → 展开表节点 → 点击字段 → 字段详情弹窗链路”。任一步缺失均应失败并保留截图、弹窗文本和网络响应作为证据。

## 8. 当前第一版实施边界（已确认）

1. SFTP 连接、目录 `/source`、解析规则和自动建表配置，直接复用此前已跑通的 SFTP 文件接入配置；仅将实际读取文件名替换为本套 `e2e_lineage_sftp_yyyyMMdd` 文件。
2. 不增加 `LINEAGE_SFTP_DATE` 等日期覆盖参数。初始化按执行当天选择文件；远端可用日期不足时，由人工补充对应日期文件后再执行。
3. 文件/SFTP 来源接入及数据地图目标表任务调度均使用 GBase / `G_BASE_DB`、生产脚本、任务名和重试次数。调度周期、责任人和告警不是本轮字段血缘测试范围。
4. 主脚本保存并将目标表上线后，固定等待 1 秒，直接进入数据血缘验证；不额外等待“解析完成”状态。
5. 前端更新后先按实际页面确认字段详情弹窗结构，再实现自动化断言。第一版只验证本清单主 SQL 的字段链路。
6. `CASE WHEN`、聚合、`CAST`、`NULL` 和中间表传递等复杂场景，在主链路跑通后按相同夹具模式逐条扩展，每条 SQL 使用独立目标表。
